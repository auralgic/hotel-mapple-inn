# Hotel Mapple Inn Jaipur --- Hotel Management + QR Room Service Web App

## Product Requirements, Architecture, UX, Database, API, Security and Copywriting Specification

> Project: Hotel Mapple Inn, Plot No. 408--409, Nirman Nagar,
> Mansarovar, Jaipur, Rajasthan, India
>
> Property size: 16 rooms
>
> Primary goal: Build a low-cost, production-usable hotel web app where
> hotel staff can manage rooms, guests, food orders, payments, menu
> items and operational status from one dashboard, while guests can scan
> a unique QR code in their room to order food.

## 1. The biggest architectural decision

Do NOT build this as a React frontend connected directly to Google
Sheets and Google Drive.

That architecture is attractive because it looks free, but it creates
avoidable problems around concurrent orders, authentication, payment
records, row-level security, data relationships and reliable updates.

For this hotel, the better low-budget architecture is:

-   Frontend: React + Vite + TypeScript
-   UI: Tailwind CSS + shadcn/ui
-   Backend/database/auth/storage: Supabase
-   Hosting: Vercel or Cloudflare Pages
-   QR codes: generated by the app
-   Payments: UPI intent/deep-link for the low-cost MVP; payment gateway
    integration later for automatic verification
-   Google Drive: optional backup/export destination, not the primary
    database
-   Google Sheets: optional reporting/export, not the transactional
    database

This is appropriate for a 16-room property because the data volume is
small but the system still needs transactional consistency.

## 2. Important payment reality

A static UPI QR code does NOT give the website reliable automatic
confirmation that a payment was received.

The app may show the guest the amount and a UPI QR/deep link, but unless
a payment provider/API is integrated, the system cannot safely assume
that a successful-looking payment screen means the hotel's bank account
received the money.

Therefore the MVP must have two payment states:

-   Pending verification
-   Verified

Recommended low-budget flow:

1.  Guest creates order.
2.  App calculates the exact total.
3.  App generates a UPI payment link/QR containing the amount.
4.  Guest pays through a UPI app.
5.  Guest enters the UPI transaction/reference ID and optionally uploads
    a payment screenshot.
6.  Staff sees the order in the dashboard.
7.  Staff verifies the payment and clicks "Verify Payment".
8.  Order moves to "Paid / Preparing".

For fully automatic payment confirmation, integrate a payment gateway
such as Razorpay/Cashfree/another suitable provider after the MVP is
working.

Never mark an order as paid merely because the guest clicked "I Have
Paid".

## 4. Core guest experience

Every room has a unique QR code.

Example:

Room 101 QR: https://hotel-domain.com/order?room=101&token=SIGNED_TOKEN

Room 102 QR: https://hotel-domain.com/order?room=102&token=SIGNED_TOKEN

Do not use only a plain room number without a token in production.

Guest flow:

Scan QR → Hotel branded landing/menu → Browse categories → Select items
→ Add to cart → Review order → Confirm room → Enter guest name or
optional identifier → Select payment → Show UPI amount/QR → Pay → Enter
transaction reference → Submit order → Receive order confirmation →
Track status

The guest should never need to download an app.

## 18. Security model

Use Supabase Auth for staff.

Never put Supabase service-role keys in React.

Frontend may use the public/anon key only with Row Level Security
configured correctly.

Database policies must ensure:

-   Guests cannot read other guest orders.
-   Guests cannot modify arbitrary rooms.
-   Staff can access only the resources allowed by their role.
-   Kitchen users cannot change financial settings.
-   Normal staff cannot modify audit logs.
-   Public menu access exposes only active menu items.
-   Public room QR access does not expose private guest information.

For guest room access, use a signed/revocable QR token.

Do not trust:

`?room=101`

as proof that the user is physically in room 101.

The QR should contain a non-guessable token and the backend should
validate it.

## 19. Guest session model

When a QR is scanned:

1.  Validate QR token.
2.  Resolve room.
3.  Create an anonymous guest session.
4.  Store session ID in browser local storage/cookie.
5.  Attach orders to the session.
6.  Allow order tracking only for that session.

Do not expose all orders for a room to anyone who knows the room number.

## 29. Error handling

Every action needs a useful error message.

Bad:

"Error 500"

Better:

"We couldn't place your order. Please check your internet connection and
try again."

Payment error:

"We couldn't save your payment reference. Your order has not been marked
as paid."

Duplicate submission protection is mandatory.

If a guest taps "Place Order" multiple times, the system must not create
multiple orders.

Use an idempotency key for order creation.

## 30. Offline/poor-network behaviour

Because guests may have weak Wi-Fi/mobile internet:

-   Cache menu data
-   Show loading states
-   Preserve cart locally
-   Retry safe requests
-   Do not duplicate order submissions
-   Clearly show connection problems

Do not pretend an order was successfully placed until the server
confirms it.

## 41. Final product philosophy

The first version should solve hotel operations, not try to become a
giant hotel ERP.

The most valuable workflow is:

Guest scans QR → orders food → pays → hotel verifies → kitchen prepares
→ guest receives order → order appears in the stay folio → checkout
includes all charges

If this workflow is reliable, the product has real operational value.

Everything else should be built around making that workflow faster,
safer and easier for staff.
